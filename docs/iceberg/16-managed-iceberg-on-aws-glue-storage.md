# Managed Iceberg tables on AWS: Glue, two catalogs, and where the data is stored

Questions: with a Databricks managed Iceberg table, what can I do with it on AWS? Can I connect to it
from Glue? Can two catalogs share one Iceberg table? Where does Databricks store the table?

> Based on Databricks and AWS documentation and blogs. Not tested. ⚠️ marks points to verify.

## Short answers

- **AWS engines:** yes, a lot. Several AWS engines can read the table, and some can write to it through Unity Catalog's Iceberg REST catalog.
- **Glue:** yes, through **Glue catalog federation**, but **read-only**.
- **Two catalogs:** only one catalog can **own** an Iceberg table, and for a managed table that's Unity Catalog. A second catalog such as Glue can only *point to* Unity Catalog.
- **Where it's stored:** the files are in S3 in Unity Catalog's managed storage. The pointer to the current version and the permissions are in Unity Catalog, not in S3.

## 1. Where Databricks stores a managed Iceberg table

| Part | Where | Notes |
|---|---|---|
| **Data files** (Parquet, deletion vectors) | **S3**, in the managed storage location of the metastore, catalog or schema | That's your own bucket, registered as Unity Catalog managed storage. Path is generated by Unity Catalog, roughly `s3://<bucket>/<prefix>/__unitystorage/…/tables/<table-uuid>/` ⚠️ |
| **Iceberg metadata** (`metadata.json`, manifest lists, manifests) | **S3**, in the same table folder (`metadata/`) | Standard Iceberg files ([`14-…md`](14-managed-vs-standard-files-and-control-plane.md)) |
| **Pointer to the current `metadata.json`** | **Unity Catalog** (Databricks control plane) | That's what makes it "managed": only Unity Catalog moves it forward |
| **Permissions, row filters, masks, tags, lineage, comments** | **Unity Catalog** | Not in S3 |

⚠️ If a catalog was created on **Databricks default storage** (the serverless default on newer
accounts) instead of your own bucket, the files are in Databricks-managed storage. Then you have no
direct S3 access at all. Check the catalog's storage root with `DESCRIBE CATALOG EXTENDED`.

## 2. Can two catalogs share one Iceberg table?

| Pattern | Works? | Why |
|---|---|---|
| **Two catalogs that both write** (Unity Catalog and Glue each hold their own pointer) | ❌ | Iceberg has **one pointer per table**. Two owners split the history: each commits its own `metadata.json` and they overwrite each other's work. Unity Catalog maintenance would also delete files Glue still points to |
| **Register the managed table's `metadata.json` in Glue** (`register_table`) | ❌ Don't | A frozen copy of the pointer that goes stale with the next commit. It bypasses Unity Catalog permissions, and it breaks when predictive optimization expires snapshots |
| **Glue federates to Unity Catalog** (Glue asks Unity Catalog for the current pointer on every query) | ✅ Read-only | One owner (Unity Catalog), and Glue is just a window onto it |
| **Engines talk to Unity Catalog's Iceberg REST catalog directly** | ✅ Read and write | Unity Catalog stays the only owner of commits |

## 3. What you can do with the table on AWS

| Engine on AWS | How it connects | Read | Write |
|---|---|---|---|
| **Amazon Athena** | Glue catalog federation to Unity Catalog. Lake Formation authorizes S3 access | ✅ | ❌ |
| **Amazon Redshift** | Glue catalog federation (United Airlines case) | ✅ | ❌ |
| **AWS Glue ETL (Spark)** | Glue catalog federation, or Unity Catalog's REST catalog directly | ✅ | Only via the Unity Catalog REST catalog ⚠️ |
| **Amazon EMR (Spark, Trino, Flink)** | Unity Catalog's REST catalog (`/api/2.1/unity-catalog/iceberg-rest`), or Glue federation for reads | ✅ | ✅ via the REST catalog |
| **Trino / Starburst, PyIceberg, Snowflake** | Unity Catalog's REST catalog | ✅ | ✅ (Trino, Spark, Flink, Snowflake are named as write clients) |
| **Databricks on AWS** | Native | ✅ | ✅ |
| **Direct S3 access to the files** | — | ⚠️ Emergency only ([`12-…md`](12-managed-iceberg-summary-aws-azure.md) §2.3) | ❌ |

### Glue federation setup, in outline

1. A Databricks **service principal** (OAuth) with `SELECT` on the tables, and external data access enabled on the metastore.
2. In AWS Lake Formation / Glue, a **federated catalog** connected to Unity Catalog with those OAuth credentials.
3. Lake Formation permissions for the Athena / Redshift users.
4. Query with `SELECT * FROM "uc_federated"."sales"."orders"` in Athena.

It covers **Iceberg tables and Delta tables with Iceberg reads (UniForm)**, read-only. Glue looks up
the current metadata at query time, so reads are always current.

## Summary

| Question | Answer |
|---|---|
| Can I use the table from AWS services? | ✅ Athena, Redshift, Glue ETL, EMR, Trino… |
| Can I connect to it from Glue? | ✅ Through **Glue catalog federation**, read-only |
| Can two catalogs own one Iceberg table? | ❌ One owner per table. Unity Catalog owns managed tables. Others can only federate (read) or write *through* Unity Catalog |
| Where is the table stored? | Files (data + Iceberg metadata) in **S3** (your managed storage bucket, unless it's Databricks default storage). Pointer and permissions in **Unity Catalog** |

**Rule of thumb:** reads from AWS engines can go through Glue federation, Lake Formation and Athena
or Redshift. Writes always go through Unity Catalog, either in Databricks or with an engine using its
REST catalog. Never give Glue its own pointer to the same files.
